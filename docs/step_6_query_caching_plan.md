# Implementation Plan — Step 6: Query Caching

## Goal
Implement a robust caching layer to intercept common legal queries *before* they hit the Indian Kanoon API and the primary LLM, significantly reducing per-query API costs (₹0.50–0.90) and reducing latency to near zero for repeat questions.

## Architecture & Logic

We will use the **rewritten search query** (generated by the LLM in `src/retrieval/rewrite.py`) as the unique cache key. Because the LLM normalizes different citizen questions (e.g., *"landlord won't give back my money"* and *"how to get security deposit back from owner"*) into the same standardized legal search query (e.g., `"security deposit" ANDD tenancy ANDD refund doctypes: laws`), this makes for a highly effective semantic cache key.

### 1. Database Schema (`src/db.py`)
We will create a new SQLite table called `query_cache`:
- `search_query` (TEXT PRIMARY KEY) — The normalized string used as the cache key.
- `context_text` (TEXT) — The concatenated legal documents retrieved from IKanoon.
- `citations` (TEXT) — JSON-serialized citation metadata.
- `llm_answer` (TEXT) — The plain-language answer generated by the LLM.
- `created_at` (TEXT) — Timestamp.

### 2. Pipeline Refactoring (`src/pipeline.py` & `src/retrieval/context.py`)
Currently, the pipeline calls `build_context(question)`, which internally calls `rewrite_query`, searches IKanoon, and formats the context. Then the pipeline calls `explain_with_llm`. 

We will refactor this so the flow is:
1. **Query Construction**: `pipeline.py` calls `rewrite_query(question)`.
2. **Cache Check**: Check the `query_cache` table for the exact `search_query` string.
   - **Cache HIT**: Instantly return the cached `llm_answer` and `citations`. Update the session with the cached `context_text`. (Saves 1 IKanoon Search, 2-3 IKanoon Doc fetches, and 1 massive LLM generation).
   - **Cache MISS**: Proceed to call `build_context` (passing the `search_query`), run `explain_with_llm`, and then `INSERT INTO query_cache` so future identical queries are free.
